PROJECT 01 / CAPSTONE

ScamCheck

A cloud-based web application that helps users assess suspicious URLs, phone numbers and screenshots for potential scam indicators.

Azure Python Flask Docker PostgreSQL Azure DevOps CI/CD Monitoring

OVERVIEW

The problem

Scam messages can arrive through different channels and often contain suspicious links, phone numbers or screenshots of conversations. Checking each of these separately can make it difficult for users to quickly assess potential warning signs.

I developed ScamCheck as my Cloud and DevOps capstone project to provide a centralised web application where users can analyse these different types of suspicious content from one interface.

SOLUTION

What I built

ScamCheck is a Flask web application that combines several scanning methods into a single platform. Users can submit suspicious URLs, phone numbers or screenshots and receive a risk assessment together with indicators and recommended actions.

01
URL Analysis

Checks suspicious URLs using Google Safe Browsing and presents the result in a user-friendly format.

02
Phone Number Analysis

Checks phone numbers and provides information that can help users identify suspicious callers.

03
Screenshot Analysis

Uses AI-assisted analysis to identify potential scam indicators within uploaded screenshots.

04
Scan History

Authenticated users can review their previous scan activity and results.

ARCHITECTURE

Designing the cloud solution

I designed the application primarily around managed Azure services so that I could focus on application development and deployment without having to manage the underlying operating systems and servers.

The Flask application runs as a Docker container on Azure App Service. Application data is stored in Azure Database for PostgreSQL, while Azure Key Vault is used to securely manage application secrets and third-party API credentials.

Azure Monitor, Application Insights and Log Analytics provide application telemetry and monitoring, while Azure DevOps handles the automated CI/CD workflow.

CI/CD

Automating deployment

I implemented a CI/CD pipeline using Azure DevOps to make application releases more consistent and reduce the number of manual deployment steps.

When a new version is released, the pipeline runs the automated tests, builds a Docker image and pushes the image to Docker Hub. The new version is then deployed to the App Service staging slot.

A health check verifies that the application is responding successfully before the staging slot is swapped into production.

DEPLOYMENT

Staging before production

Instead of deploying a new version directly to production, I used an Azure App Service deployment slot as the staging environment.

The new container is started in staging and checked through the application's health endpoint. Once the application is healthy, the staging and production slots are swapped.

This approach provides an additional validation step before the new version receives production traffic.

SECURITY

Protecting application secrets

I avoided storing sensitive API credentials directly in the source code by using Azure Key Vault for secret management.

Azure App Service uses a Managed Identity, giving the application its own identity within Azure without requiring separate Azure credentials to be stored in the application.

Role-Based Access Control determines what that identity can access. This follows the principle of least privilege by granting the application only the permissions required for its operation.

DATABASE

Moving to managed PostgreSQL

During development I initially worked with local database options before migrating the application data to Azure Database for PostgreSQL Flexible Server.

PostgreSQL stores application data including users, scan history, bulletins and flagged phone number information. Using a managed database also separates persistent application data from the App Service container.

MONITORING

Understanding application health

I integrated Application Insights and Log Analytics to collect telemetry from the deployed application.

Monitoring data can then be visualised through dashboards, allowing application behaviour and infrastructure metrics to be observed from a central location.

SCALABILITY

Testing autoscaling

I configured Azure App Service autoscaling and performed load testing to observe how the application responded as demand increased.

During the demonstration, the environment was configured to scale between two and five instances. Under simulated load, the application scaled out progressively and later scaled back in as demand decreased.

TESTING

Building confidence before release

I developed automated tests covering important application functionality including page access, authentication, administration and scanner workflows.

The final test suite contained 24 automated tests. These tests are executed by the CI/CD pipeline before a new Docker image proceeds through the deployment process.

REFLECTION

What I learnt

ScamCheck gave me practical experience connecting application development with cloud infrastructure and DevOps practices. Rather than focusing only on building the Flask application, I had to consider how the application would be deployed, secured, monitored and updated.

Troubleshooting database connectivity, application configuration, deployment health checks and CI/CD issues also helped me become more systematic when investigating problems across different layers of an application.

The project helped me better understand how managed cloud services, containers, CI/CD, monitoring and security controls work together as part of a complete application deployment.
